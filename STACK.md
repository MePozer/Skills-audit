# STACK.md — baseline стека проекта

Единый источник текущего проектного baseline. Скиллы набора не хранят версии как независимый источник истины: они ссылаются сюда и помнят, на чём проверялись.

Читать этот файл обязательно, если задача касается версий, зависимостей, совместимости, сборки, обновления компонентов или поведения, зависящего от версии. Имя файла само по себе ничего не гарантирует — решение читать его принимает агент по этим признакам.

| ReGameDLL_CS | 5.30.0.814 | совпало, строка `5.30.0.814-dev` | `meta list` |
| HLDS / Protocol | 8684 / 48 | совпало, Exe `1.1.2.7/Stdio`, build `4419` | `meta list` |

**Про ReAPI отдельно, чтобы это не «исправляли» задним числом.** `5.29.0.358` — релизный артефакт, который проект взял как baseline. `5.29.0.359-dev` — строка версии, которую печатает сам модуль: номер берётся сборкой из счётчика коммитов и поэтому выше номера релиза. Это разные понятия:

- baseline/release: `5.29.0.358`;
- live installed/observed: `5.29.0.359-dev`;
- live verification date: `20.09.2026`.

Ни переименовывать baseline в `359`, ни считать сервер собранным на `358` нельзя. Версию компонента подтверждать выводом модуля, а не именем архива.

## Baseline ≠ Installed ≠ Verified

Три разных понятия, которые нельзя смешивать:

- **Baseline** — версии, которые проект считает своим проверенным набором. Скиллы опираются на него. Хранится здесь, в одном месте.
- **Installed** — что реально лежит в папке сервера и что печатает сам сервер. Может отличаться от baseline; пример — ReAPI.
- **Verified** — что реально проверено вместе и когда. Baseline verified на дату выше; installed может быть verified лишь частично.

Следствие для формулировок: утверждение «правило проверено» относится к baseline и дате проверки. Утверждение «на сервере стоит X» относится к installed и требует вывода команды, а не памяти.

## Upgrade policy

1. Baseline не вечен: он фиксирует проверенное состояние, а не запрет на обновление.
2. Новая версия не считается автоматически совместимой.
3. И наоборот: версия не считается несовместимой только потому, что номер отличается.
4. Перед обновлением прочитать changelog / release notes именно этой версии.
5. Проверить, какие API и какое поведение затронуты, и какие скиллы на них опираются.
6. Выполнить компиляцию: `0 errors, 0 warnings`, `debug >= 1`, без `-d0`.
7. Выполнить runtime-проверку, если это возможно. Если невозможно — записать пункт как непроверенный, а не как проверенный.
8. Только после этого обновлять baseline в этом файле и в затронутых скиллах.
9. Старую запись переносить в историю ниже, а не удалять: скиллы и правила теряют смысл без даты, на которую они проверялись.
10. Обновление без этой процедуры = baseline не обновлён. Молча «подтянуть» версию в тексте нельзя.

## Как проверить расхождение (drift)

| Команда | Что показывает |
| --- | --- |
| `meta list` | Metamod, движок, Protocol, Exe, build, версии модулей |
| `amxx modules` | модули AMX Mod X, версия ReAPI, источник загрузки |
| `version` | версия движка |
| `amxx cvars sv_rehlds_*` | фактические значения cvar ReHLDS |

Сравнить вывод с таблицами выше. Расхождение — не сбой, а вход в процедуру обновления: сначала определить реальную версию, потом проверять совместимость.
